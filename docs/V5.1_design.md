## 修改摘要

原 V5 将 Query Plan 表示为开放三元组模式、变量绑定、运算和约束，将工作记忆表示为已验证三元组图，并由 Runtime 承担关系匹配、精确回调和部分比较、归约及规则运算。[V5：方案摘要，pp.2–3；§3.2–3.6，pp.9–11；§4.7–4.9，pp.15–17]

新版保留其“计划、事实、执行状态分离”的原则，但把主要语言接口改为自然语言证据需求和完整事实。Runtime 不再承担通用自然语言关系理解，也不强制执行最终比较或构造派生事实图。

| 修改对象 | 原 V5 | V5.1 的处理 |
|---|---|---|
| Query Plan 节点 | 开放三元组模式及相关运算描述 | 自然语言子 query，保留 ID、依赖、输出变量和状态 |
| 工作记忆节点 | 实体；三元组关系承载事实 | 有原文来源、语义完整的原子事实 |
| 工作记忆边 | 实体间的语义关系 | 事实在本题中通过变量绑定形成的衔接；不默认添加推导依赖边 |
| 未绑定证据 | 按实体、relation family 等索引保存 | 按 query ID 保存完整候选事实；绑定后语义复核 |
| 语言接口 | Triple Event / JSON 等结构化输出 | 简短事实行，加 COMMIT / DEFER；另用短 BIND 行报告子问题结果 |
| 最终比较与综合推理 | Runtime 运算、DERIVED triple、Operator Trace | 原始证据交给 Answer；不强制生成派生节点 |
| 影响后续搜索的中间推理 | 显式运算执行 | 同一个 Agent 按需得出有证据引用的中间绑定，不必写入事实图 |
| callback | Binding-Triggered Exact Callback | Binding-Triggered Candidate Review：绑定触发的候选复核 |
| 主体结构 | 一个共享 Agent + Runtime | 保留；仍使用 PLAN、UPDATE、VERIFY、ANSWER 四类接口 |

**本次不加入：**独立连边 Agent、独立 Planner 模型、GNN、图数据库、自由生成的关系标签体系、大型运算图或新的强化学习算法。是否训练、是否引入更复杂的检索筛选，放到表示与机制对照实验之后决定。

# 1 问题定义：保留任务，修改表示和职责

## 1.1 保持不变的任务设定

系统接收原问题和分块长文档，按给定顺序逐窗口阅读，不能在阅读开始前访问未来窗口，也不能提前构建全文事实图。系统可保存已经读过的原文及来源索引，但进入每次模型调用的活跃上下文受到预算约束。目标仍是在这一约束下保留足够证据，完成多跳问答，而不是尽可能构造完整知识图谱。[原版依据：V5 §1.1–1.3，pp.4–5]

原问题始终作为阅读和回答的依据。Query Plan 是可修正的证据收集指引，不是取代原问题的唯一任务定义。

## 1.2 重新明确“延迟绑定”

新版将两个判断分开：

**事实内容成立：**原文是否支持一条具体陈述，例如“Alice 的母亲是 Mary”。

**任务角色成立：**Alice 是否就是本题需要寻找的老师，以及这条事实是否能用于回答“目标老师的母亲是谁”。

前者可能在早期阅读时就能够确定，后者可能必须等待另一条事实。因此，DEFER 保存的是已经具体化的候选事实，延迟的是它对某个 query 的任务绑定，而不是把事实改写成一个含未知变量的半成品。

可直接替换原问题定义中的核心表述：

> 在顺序阅读过程中，一条事实的语义内容可能已经完整，但其在当前问题中的用途仍取决于尚未获得的上游信息。系统先保存与未完成证据需求相容的完整候选事实；当后续证据确定相应对象或值时，再验证候选事实能否承担该证据需求，并将匹配事实接入活跃工作记忆。

## 1.3 新版的三部分状态

计划 P 由自然语言子 query 和依赖组成；事实工作记忆 G 由活跃事实及其绑定衔接组成；Runtime 维护来源、候选记录、绑定及执行日志。三者仍然分开。

```text
Query Plan：还需要知道什么，以及哪些未知量依赖前序结果。
事实工作记忆：已经确认哪些事实可以用于当前问题。
Runtime：保存、激活、回查、验证结果应用、预算与日志。
```

一次 UPDATE 的输入为“原问题 + 当前计划视图 + 活跃事实视图 + 当前窗口”。外部候选区和完整原文归档不自动进入 prompt；只有被调度复核的候选及其原文进入对应 VERIFY 调用。

# 2 研究动机：从表示约束转向证据用途后显

## 2.1 保留 V5 的主问题，不重新扩大研究范围

V5 的切入点仍然是：证据出现的顺序可能与其用途被确定的顺序不同，早期信息可能在尚不能确定任务角色时被丢弃。[V5 §1.2，p.4；§2.4–2.5，p.8]

本次修改不是改做离线 Graph RAG、长期用户记忆或通用符号推理系统。原第 2 节的相关工作介绍不因换了表示就自动失效，但其中用于定位本方法的“开放三元组”“relation family 精确查找”等描述应同步修改。

## 2.2 新版需要验证的具体动机

原 V5 使用显式关系模式约束证据提取。新版提出一个待验证的设计假设：采用自然语言子问题和完整事实，可能减少模型在固定关系表达、严格结构化输出和证据语义之间来回转换的负担，同时继续通过依赖、来源与状态维持流程约束。

这只是设计假设，不是已证明的收益。自然语言匹配也可能带来误匹配、候选增多和复核成本上升，必须与原版使用同一数据和模型进行比较。

## 2.3 新版切入点的写法

研究问题可以集中为：

> 在有限活跃上下文的顺序阅读中，如何利用尚未具体化的证据需求，提前保存可能有用的完整事实，并在后续绑定出现时准确恢复其任务用途？

“自然语言子问题”“事实作为节点”是服务这一机制的表示选择，不单独作为未经调研证明的新颖性结论。

# 3 核心定义与边界

## 3.1 Query Plan：自然语言子问题依赖图

用自然语言 query 替换原开放三元组模式。一个 query 表示一项需要收集或确定的证据信息；串行题通常可以按跳拆分，但不强制“每一步最终推理都必须建一个 query”。比较题可以包含并行分支。

以下人物关系均为说明流程的假设例子。

```text
原问题：Cindy 的老师的母亲出生在哪个城市？

Q1 [ACTIVE]
query：Cindy 的老师是谁？
output：?teacher
depends_on：无

Q2 [DORMANT]
query：?teacher 的母亲是谁？
output：?mother
depends_on：Q1

Q3 [DORMANT]
query：?mother 出生在哪个城市？
output：?city
depends_on：Q2
```

依赖边表示“后一个 query 需要前一个 query 产生的输入”，不是事实之间的现实关系。上述依赖为 Q1 → Q2 → Q3。

计划的最小持久化字段如下。程序内部可用字典或 JSON 存储，但不要求模型按大 JSON 输出。

| 字段 | 内容 | 维护方 |
|---|---|---|
| id | 稳定的 query 编号，例如 Q2 | 初始 PLAN 提出，Runtime 校验 |
| template | 包含必要占位符的自然语言问题 | PLAN；必要时局部修正 |
| depends_on | 输入所依赖的上游 query ID | PLAN 提出，Runtime 检查 |
| output | 当前 query 回答后填入的变量名 | PLAN 提出 |
| status | DORMANT / ACTIVE / RESOLVED | Runtime 维护 |
| result、support_refs | 当前结果及支持来源；未解决时为空 | Agent 提出，Runtime 验证后记录 |

`rendered_query` 根据模板和当前绑定临时生成，不覆盖模板。变量替换必须按完整变量标识处理，避免把 `?person` 错替换进 `?person2`。

Runtime 检查依赖是否存在、图是否无环、输入占位符是否有来源、输出变量是否冲突。复杂题可额外指定“需要完整集合”，但不引入通用关系本体或 operator registry。

## 3.2 三种 query 状态

| 状态 | 严格含义 | 阅读行为 |
|---|---|---|
| DORMANT | 至少一个必要的输入对象或值尚未确定 | 仍检查符合该证据需求的事实；先保存候选 |
| ACTIVE | 必要输入已确定，但子问题尚未获得足够支持 | 对具体对象收集可用事实；达到充分条件后提出 BIND |
| RESOLVED | 当前已有足够证据支持一个符合问题要求的结果 | 向下游提供结果，并保留来源；允许后续纠错 |

**输出未知不意味着 DORMANT。** Q1 的答案 `?teacher` 未知，但输入 Cindy 已知，因此它从 ACTIVE 开始。

**激活不意味着解决。** `?teacher = Alice` 只能让 Q2 变成“Alice 的母亲是谁”，不能自动让 Q2 得到结果。

常规转移是 DORMANT → ACTIVE → RESOLVED。若支持被撤销、上游绑定改变或出现未解决冲突，相关 query 可退回 ACTIVE；若必要输入重新变为未知，则回到 DORMANT。不要为每种异常都新增一种状态，异常原因记录在 Runtime 日志中即可。

## 3.3 占位符语义：放宽对象，保留关系和条件

`?xx` 表示尚未确定的输入对象或值。阅读 DORMANT query 时，允许把原文中的具体对象作为临时代入对象，但必须保留 query 已经明确的关系、角色方向和限定条件。

对于“?teacher 的母亲是谁”：

| 原文事实 | 是否可作为候选 | 原因 |
|---|---|---|
| Alice 的母亲是 Mary | 可以 DEFER | 母亲关系成立；Alice 是否为目标老师仍待后续确定 |
| Mary 是 Alice 的母亲 | 可以 DEFER | 同一关系的自然语言改写 |
| Alice 是一名老师 | 不能仅据此匹配这个 query | 它没有提供母亲关系 |
| Alice 的父亲是 Tom | 不作为母亲关系的替代证据 | 关系不符合 |
| Alice 的母亲不是 Mary | 可以保留为相关限制或冲突证据，但不能绑定 Mary 为答案 | 否定必须保留，不能当作正向答案 |

早期候选不必同时证明“该对象就是上游最终需要的人”，否则又会漏掉等待绑定的事实。但事实中被隐藏或省略的角色必须通过当前可见原文恢复；无法恢复时不能凭空补全。

## 3.4 事实节点：完整的来源事实，而不是填空后的 query

事实节点包含一条相对自足的原子陈述和其来源。最小字段为 `fact_id、text、source_refs`。必要的时间、否定、范围和身份限定保留在 `text` 中；既有代码如已维护 qualifiers，可以继续存储，但不强制模型重复输出。

```text
F1
text：Alice 的母亲是 Mary。
source_refs：c02:s1
```

不能把它保存成“?teacher 的母亲是 Mary”，也不能因为暂时属于 Q2 的候选，就把 Alice 的实际名字删掉。

原文一句包含两个独立断言时可以拆成两个事实；一个断言所需的条件不能为了“原子化”被拆掉。规范化代词或省略主体时，`source_refs` 应包含支持补全的前文，而不只是孤立的代词句。

第一版可以复用原三元组记录中的来源和限定条件，将其转为完整事实正文；旧的 subject / predicate / object 只作为兼容字段，不再是新版模型接口的必填项。

## 3.5 事实图的边：绑定衔接，不是推导运算图

新版默认只记录事实在当前任务中的绑定衔接。例如：

```text
F1：Cindy 的老师是 Alice。
F2：Alice 的母亲是 Mary。

F1 → F2：F1 确定了 ?teacher = Alice，F2 经核验可用于该实例化 query。
```

这条边不是“F1 蕴含 F2”，也不是现实中的因果关系。它记录两条独立事实为何能在本题中接起来。

边由已确认的 query 结果、支持来源和候选提升事件产生，不进行全图两两相似度连边。不因为共享名字就直接连接；同名、时间范围和身份不相容的情况仍须检查。

每条连接至少能够追溯到：上游支持事实、下游事实、对应 query、绑定变量及值。一个绑定由多条事实支持时，保留支持事实的集合引用，不把它误写成其中任意一条都能独立完成绑定。

**本次删除强制推导依赖边。** 最终比较、归纳和综合推理交给 Answer；不必先生成 DERIVED 节点。某次中间推理若仅产生控制后续检索的结果，它保存在 query 的 result 与 support_refs 中，不伪装成原文事实。

## 3.6 Deferred Workspace：按 query 路由的外部候选区

保留 `Deferred Workspace` 名称，中文统一为“延迟候选区”。它保存已经读到、可能满足某个 query，但尚未被接受为该 query 当前证据的完整事实。

基本查找入口从原来的实体—关系语义键，改为 `query_id → 候选 fact_id 集合`。事实正文只保存一份，候选记录引用它。

```text
Q2：
  F1：Alice 的母亲是 Mary。 [c02:s1]
  F4：Bob 的母亲是 Jane。   [c07:s2]

Q3：
  F2：Mary 出生于苏州。    [c05:s1]
```

DEFER / COMMIT 是“事实对某个 query、某次绑定的使用状态”，不是事实永久的全局属性。一条事实可以已被 Q1 接受，同时仍是 Q3 的候选。

一次复核中不匹配 Alice 的事实，不必从存储中物理删除；如果绑定后来变为 Bob，应允许重新检查。复核结果需关联 query 版本和绑定版本，不能沿用过时的拒绝或接受结论。

集合成员已知但枚举未完整，不属于“对象未绑定”。沿用原 V5 对 OPEN 集合的外部记录职责，但与未绑定候选分开标记；不把所有未完成状态统一叫 DEFER-UNBOUND。[原版依据：V5 §3.6，p.11；§5.5，p.19]

## 3.7 Raw Archive：保持不变

保存已读原文和稳定 source ID。callback 恢复原文后核验，不把模型先前生成的事实文本本身视为独立的原文证据。

所有引用必须来自当前已读前缀。任何候选预抽取、索引或回调，都不能在主实验中读取尚未到达的窗口。[原版依据：V5 §3.7，p.11]

## 3.8 活跃工作记忆与完整执行状态

| 内容 | 是否持续进入 UPDATE prompt | 管理原则 |
|---|---|---|
| 原问题 | 是 | 防止计划取代真实任务 |
| Query Plan 视图 | 是 | 保留全部 ACTIVE 和 DORMANT 的必要需求；已解决部分可紧凑呈现 |
| 活跃事实与必要衔接 | 是 | 受 token 预算约束 |
| 延迟候选区 | 否 | 绑定或候选事件触发时定向复核 |
| 已验证但暂不显示的事实 | 否 | 来源和接受记录仍在，可按需恢复 |
| Raw Archive | 否 | 仅恢复本次需要核验的已读片段 |
| 完整状态与执行日志 | 否 | 由 Runtime 保存，不全量序列化 |

事实暂时离开活跃视图，不代表它重新变成“未绑定事实”。第一版不新增复杂链条折叠算法，但应区分“是否可用于本题”和“是否当前显示”。

预算应按实际序列化 token 计算，不能只限制节点个数。若必要证据包本身超过预算，应显式记录预算瓶颈，不能悄悄丢掉来源或声称仍保留了完整证据。

## 3.9 最终输出对象：Evidence Pack

将原 §3.9 的“Minimal Evidence Subgraph + Operator Trace”替换为“可追溯证据包”。其中包含用于回答的完整事实、必要的对象对应关系和 source_refs；不强制携带整个计划、候选区和执行日志。

不宣称得到数学意义上最小的证据子图，也不要求证据包始终是最后一刻活跃视图的子图。因预算暂时不显示、但仍已验证的支持事实，可以从 Runtime 的来源记录恢复；恢复与最终输入成本都要统计。

# 4 核心框架：一个共享 Agent，四类接口，轻量 Runtime

## 4.1 保持单 Agent 架构

PLAN、UPDATE、VERIFY、ANSWER 继续使用同一个模型，通过不同提示词区分任务，不新增独立 Planner 或连边 Agent。[原版依据：V5 §4.1–4.3，pp.13–14]

```text
原问题 → PLAN：自然语言子问题与依赖

当前窗口 + 计划视图 + 活跃事实
    → UPDATE：事实事件 / BIND 建议 / 必要的计划提示
    → Runtime：保存、校验、绑定、状态更新

新绑定或待核验的新候选
    → query 定向候选检索
    → 恢复已读原文
    → VERIFY：语义匹配与结果建议
    → Runtime：PROMOTE、传播新绑定

已读证据 → 充分性检查 → Evidence Pack → ANSWER
```

## 4.2 四接口的新版输入输出

| 接口 | 主要输入 | 主要输出 |
|---|---|---|
| PLAN | 原问题 | 自然语言 query、依赖、输出变量；不填入未见证据的答案 |
| UPDATE | 原问题、计划视图、活跃事实、当前窗口 | 事实行；可选 BIND；少量 PLAN_HINT |
| VERIFY | 具体化 query、当前绑定依据、候选事实及原文 | MATCH / MISMATCH / UNCERTAIN / CONFLICT；可选 BIND |
| ANSWER | 原问题、可追溯证据包 | 按既有评测格式输出答案，由模型完成最终推理 |

充分性检查和必要的中间结果确认可以复用 VERIFY 的提示词模式，不因此新增第五个独立模型。

## 4.3 事件格式：避免全量 JSON，保留可解析的最小标记

建议采用固定的一行格式：

```text
query_id | source_refs | 完整事实 | COMMIT或DEFER
BIND | query_id | 结果值 | 支持结果的source_refs
```

例子：

```text
Q2 | c02:s1 | Alice 的母亲是 Mary。 | DEFER
Q1 | c20:s1 | Cindy 的老师是 Alice。 | COMMIT
BIND | Q1 | Alice | c20:s1
```

`source_refs` 可用逗号分隔多个来源。事实正文中的换行或分隔符必须转义，或者由解析器按前三个逻辑字段及末尾动作标记解析；不能用全文搜索“defer”来决定动作。

用户可读的“[Q2 @ c02:s1] Alice 的母亲是 Mary。（defer）”可以作为兼容输入，经解析器规范化为同一种内部事件。正式实验固定一种输出格式，不交替使用多套语法。

**COMMIT 不等于 RESOLVED。** 它只表示事实可用于当前 query；只有证据足以支持该 query 的完整结果，才输出 BIND。结果值不是三元组，也不是新增事实节点。

**BIND 不是程序自动抽名字。** Agent 明确给出结果，Runtime 检查 query 是否 ACTIVE、支持来源是否有效、这些来源是否对应已接受事实，以及是否存在已知冲突。程序无法独立证明自然语言推理正确，必要时由 VERIFY 确认。

同一 source span 对应多个原子事实时，应记录其中用于绑定的事实引用；第一版无法细分时保守保留该支持 span 下相关的已接受事实，而不是任意选一个。

无相关事实时不生成事实行。程序可记录 SKIP/no-op，但不要求模型为每个无关句子输出 SKIP。

## 4.4 Runtime：确定性调度，不冒充语义理解器

将原 VALIDATE → ENTITY RESOLVE → MATCH → APPLY → BIND → EXACT LOOKUP → EXECUTE → SUFFICIENCY，改为下面的职责链。[原版依据：V5 §4.7，pp.15–16]

**第一步：验证输入。** 检查语法、query ID、来源是否属于已读原文、绑定支持是否存在。格式错误不得静默应用；修复重试和失败必须计入日志。

**第二步：先保存本窗口的所有事实事件。** 同一个窗口里可能同时出现上游和下游事实，应先接收它们，再处理绑定，以免事件输出顺序影响可见候选。

**第三步：按当前状态应用事件。** 对 ACTIVE query 的有效 COMMIT 保存为可用事实；DORMANT query 的 COMMIT 建议应降为候选，不允许越过未满足的依赖。对输入已确定的 query，仍被标记 DEFER 的新事实可进入待复核队列，而不是永久搁置。RESOLVED query 收到可能修正其结果的新证据时，也需要复核，不能因为已有结果就忽略。

普通 COMMIT 的事实适用性主要由 UPDATE 判断，Runtime 执行结构和来源合法性检查；PROMOTE 则经过单独的候选 VERIFY。日志应区分这两种接受路径，不能把所有 COMMIT 描述为经过独立语义复核。来源编号存在也不等于原文必然支持模型的改写。

**第四步：验证并应用 BIND。** 更新 result、support_refs 和绑定版本，把 query 标为 RESOLVED，并重新计算下游状态。未满足依赖或没有有效支持的 BIND 不接受。

**第五步：处理事件队列。** 新绑定、已激活 query 收到新的候选、query 局部修正，都可触发定向复核。复核产生的新绑定继续传播，直到本轮没有新事件。

**第六步：构造活跃视图和记录成本。** 不重写所有历史事实；尽量只序列化当前需要的事实和状态摘要。

这仍然是 Deterministic Runtime：确定的是状态转移和调用调度，不是自然语言语义判断。语义判断由共享 Agent 完成。

## 4.5 绑定触发的候选复核

将原“Binding-Triggered Exact Callback”更名为“Binding-Triggered Candidate Review”，中文统一为“绑定触发的候选复核”。

```text
BIND
→ 实例化下游 query
→ LOOKUP：取得该 query 的历史候选
→ FETCH：恢复候选原文与必要绑定依据
→ VERIFY：检查与当前具体对象、关系和条件是否相符
→ PROMOTE：将匹配事实接入活跃工作记忆
→ 如产生新 BIND，继续传播
```

第一版不要求重建实体—关系精确索引。query ID 能精确定位候选桶，但桶内哪个事实真正回答当前自然语言 query，需要模型判断，因此不再将整条主路径称为“精确语义匹配”。

候选较多时分批复核；主机制实验先扫描该桶全部已知候选，避免未经验证的 top-k 截断引入第二次遗漏。若后续增加筛选，应单独测召回率和成本，并将其标为工程变体。

对于单值 query，当前已知候选桶的各批结果应合并检查后再选择结果；不能第一批发现一个候选就停止，忽略后面已有的冲突。未来窗口出现的新冲突仍可能推翻当前结果，RESOLVED 不是永不修改的事实承诺。

还需要处理两种不能仅靠逐批候选判断完成的情况：其一，多条 MATCH 事实分布在不同批次，联合起来才足够得到结果；其二，新激活的中间选择 query 已能利用上游事实推理，但没有独立候选事实。此时复用 VERIFY，输入该 query 及其已接受的必要证据，尝试一次联合结果确认。它仍是同一个 Agent 的任务接口，不是新增运算模块。只有输入绑定或可用证据发生变化、且尚无可接受结果时才尝试；相同证据签名不反复调用，额外调用成本单独统计。

复核键至少包含 `query_version、binding_version、fact_id`。相同版本下已处理的事件不重复触发；出现新候选或绑定变化时重新处理。记录这些版本是为防止过期结论，不增加模型输出字段。

## 4.6 身份消歧：保留职责，取消强制全量结构化门槛

不再要求每条事实必须先转成 canonical triple 才能保存，但不能据此假定同名就是同一个人。已有 alias 表和 Entity Resolver 可以作为辅助；明确的同一性依据需要来源，不能只按名字字符串合并。

VERIFY 输入应包括决定当前输入对象的支持事实。例如当前目标是“电影 A 的导演 Alice”，候选是另一位同名作家的出生信息，必须允许返回 MISMATCH 或 UNCERTAIN。

不需要新建消歧 Agent，也不能宣称自然语言 query 自动解决实体归一化错误。[原版对应：V5 §4.8，p.16]

## 4.7 充分性检查：保留证据门槛，不让旧计划锁死回答

程序检查来源合法、绑定支持有效、显式冲突未被忽略、集合范围是否满足要求、证据包是否可构造。模型检查这些证据是否真正支持原问题，而不是仅检查每个 query 是否有一个字符串结果。

Query Plan 可错，因此不能把“所有计划节点都 RESOLVED”作为唯一充分条件。若已有不同但有效的证据直接支持原问题，可以经 VERIFY 确认后回答，并记录为何不再需要某个原计划节点。反过来，所有 query 都已填值也不必然意味着答案有充分支持。

第一轮机制实验建议读完预定文本范围再作最终回答，不同时引入提前停止，以免混淆收益来源。证据不足时记录原因，采用预先固定且跨方法一致的拒答或尽力回答协议，不把不完整证据记作成功闭环。

# 5 方法流程：替换原第 5 节

## 5.1 初始化

为文档窗口与句子配置稳定来源编号，初始化 Raw Archive、空事实表、空候选索引和执行日志。调用 PLAN 生成自然语言依赖计划。Runtime 校验变量来源、依赖无环和输出唯一性，计算初始状态。

没有未知输入的根 query 为 ACTIVE；依赖未满足的 query 为 DORMANT。PLAN 不从问题之外猜测实体答案，不读取未来文档。

## 5.2 顺序阅读与候选保存

UPDATE 始终看到原问题，以及所有尚未完成 query 的必要需求。ACTIVE 和 DORMANT 都参与阅读匹配，区别是能否确认其任务对象。

同一窗口先登记全部事实，再处理 BIND，再执行候选复核队列。DEFER 不触发全量活跃记忆改写；COMMIT、PROMOTE、绑定或冲突处理只更新受影响的状态。

对 RESOLVED query 不必继续重复搜集同样答案，但当前窗口若明确挑战已有关键事实或结果，应输出对应来源事实并交给 Runtime 复核。其输入对象已知，不能因此把它当成“上游未绑定”；DEFER 在这里表示尚未接受的新使用记录，而非重新定义 DORMANT。

## 5.3 完整逆序例子

原问题：“Cindy 的老师的母亲出生在哪个城市？”计划为 Q1 老师、Q2 母亲、Q3 出生城市。

**窗口 c02：**“Alice 的母亲是 Mary。”

```text
Q2 | c02:s1 | Alice 的母亲是 Mary。 | DEFER
```

Runtime 为该事实分配 F1，存入 Q2 的候选桶。Q2 仍是 DORMANT，不绑定 `?teacher = Alice`，也不绑定 `?mother = Mary`。

**窗口 c05：**“Mary 出生于苏州。”

```text
Q3 | c05:s1 | Mary 出生于苏州。 | DEFER
```

Runtime 分配 F2，存入 Q3 的候选桶。它不进入活跃图。

**窗口 c20：**“Cindy 的老师是 Alice。”

```text
Q1 | c20:s1 | Cindy 的老师是 Alice。 | COMMIT
BIND | Q1 | Alice | c20:s1
```

Runtime 分配 F3，接受 Q1 的结果，令 `?teacher = Alice`。Q2 变为 ACTIVE，当前问题是“Alice 的母亲是谁”。

复核 Q2 的历史候选及 c02 原文，F1 匹配后 PROMOTE；接受 `BIND | Q2 | Mary | c02:s1`。Q3 随即激活，复核 F2 及 c05 原文，得到 `?city = 苏州`。

活跃证据按任务衔接呈现为：

```text
F3：Cindy 的老师是 Alice。 [c20:s1]
F1：Alice 的母亲是 Mary。 [c02:s1]
F2：Mary 出生于苏州。     [c05:s1]

F3 → F1：?teacher = Alice
F1 → F2：?mother = Mary
```

F1、F2 保留初次保存时的 ID，不因提升而重新编号。阅读顺序与证据衔接顺序可以不同。最终 Answer 接收原问题与这些证据，输出苏州；query 的结果表不能代替来源事实。

## 5.4 最终比较：直接交给 Answer

问题：“电影 A 和电影 B 的导演谁更年轻？”

可以形成两个并行分支，各自寻找导演及其出生时间。工作记忆保留电影—导演对应事实和出生事实。年龄比较由 Answer 完成，不建立“更年轻”事实节点或比较依赖边。

```text
电影 A 的导演是 Alice。
电影 B 的导演是 Bob。
Alice 出生于 1985 年。
Bob 出生于 1978 年。
```

这里“出生时间”只是自然语言的证据需求，不要求所有文档出现同一个谓词。若原文只给参考时刻的年龄、年份范围等，模型需要判断是否足够比较；无法确定先后时不能仅因两条分支均有文本就认定可答。

## 5.5 影响后续寻找对象的中间推理：按需绑定

问题：“两部电影中更年轻的那位导演出生在哪个城市？”

这时比较结果决定后续要找谁，不能全部拖到最终 Answer。可以保留一个自然语言选择 query：“根据两位导演的出生信息，较年轻者是谁？”它依赖前面的导演及出生信息，输出 `?target_director`。

同一个 Agent 通过 VERIFY 模式检查这些事实，提出结果与支持来源。Runtime 保存中间 result，再激活“?target_director 出生在哪个城市”。不新增 operator registry，也不把“某人更年轻”伪装成原文事实。

中间结果若依赖多个 query，支持记录应覆盖相应人物身份与比较信息，不能只保存一个裸名字。答案不确定时继续读或保留冲突，不能强行填一个值来推动流程。

## 5.6 集合、计数和范围

“找到一个相关事实”与“集合完整”必须分开。询问所有成员时，query 可以处于 ACTIVE 并不断接收成员事实，只有预定范围闭合后才确认完整集合。

范围闭合由可审计的文档边界或明确枚举依据决定，不能仅凭模型说“足够了”。第一轮实验优先使用读完整个给定上下文的保守边界。

最终计数、集合交集或比较可以交给 Answer，不要求先生成归约事实。但需要保留用于枚举、去重和对象身份判断的证据。若某个集合运算结果决定后续检索目标，按 §5.5 处理为中间结果。

不能承诺任意规模的完整集合都能放进固定预算。必要成员证据超出预算时，应记录该瓶颈；本轮不借此扩展为无限集合运算引擎。

## 5.7 冲突、上游纠错与局部 Plan Patch

上游绑定改变时，依据该绑定建立的下游接受记录和连接需要失效并重新核验。原文事实本身不因失效而被删除。例如从 `?teacher = Alice` 改为 `?teacher = Bob`，Alice 的母亲事实仍可保存在事实表中，但不能继续作为当前 Q2 的已接受证据。

为此，Runtime 记录绑定版本和支持关系。只重新处理受影响的后继 query，不重置整个计划和原文归档。

自然语言计划仍可能遗漏需求。UPDATE 可以通过 `PLAN_HINT | source_refs | 简短说明` 保存“明确有助于原问题、但当前 query 无法容纳”的证据提示。Runtime 将相关来源登记为未路由候选，不要求每个窗口重新 PLAN。

当回调长期无匹配、事实与计划冲突或最终充分性检查失败时，对受影响的一小部分 query 做局部修正，并重新路由已保存候选。若早期证据从未被保存，仅修改计划不能凭空恢复；是否允许额外回读原文必须单独配置和记账，不隐藏在主流程里。

## 5.8 最终回答和预算管理

ANSWER 输入优先使用简洁事实文本及来源，保留必要对象对应关系。默认不传完整 JSON 图、全部 query 状态、历史候选或长执行日志，也不强制生成解释性推导过程。

回答格式沿用已采用的 benchmark-compatible direct 协议，保持最终答案解析方式不变。不能因修改记忆表示，顺手把 Answer 改成复杂 JSON 再用其分数评价记忆机制。

活跃事实筛选首先保护仍在使用的绑定依据和证据链，避免只留答案附近事实而丢掉桥接证据。真正等价且条件一致的重复事实可合并来源；同实体或同主题不等于重复。

本轮不新增学习式图压缩。先在固定预算下实现可恢复的活跃视图，分别报告证据不足和预算不足，避免把两类失败混为一谈。

# 6 训练策略：先迁移监督对象，不同步发明新训练框架

## 6.1 第一阶段保持 training-free

沿用 V5 先验证机制再训练的顺序。[V5 §6.1，p.21]

先固定同一模型、数据、窗口大小和回答格式，验证自然语言计划、事实保存与绑定回调能够稳定运行。此阶段不同时更换训练算法、引入新的奖励或增加 Agent。

## 6.2 各接口的监督对象如何迁移

| 原监督对象 | 新监督对象 |
|---|---|
| Open Triple Pattern、relation family | 自然语言 query、依赖、占位符、输出变量 |
| Triple Event | 完整事实、来源、query 路由、COMMIT / DEFER |
| canonical triple 与 exact match 核验 | 具体化 query 下的事实匹配、角色和条件兼容性 |
| 运算结果与 DERIVED triple | 必要的中间 BIND 及其支持来源；最终推理由 Answer 完成 |
| Minimal Evidence Subgraph + Operator Trace 回答 | 原问题 + 可追溯事实证据包回答 |

训练样本必须从当前已读前缀构造。生成某一步 UPDATE / BIND 标签时不能使用未来证据把尚未绑定的对象当作已知。

Oracle Plan 可以使用支持链辅助生成，但测试时不把 gold answer 或桥接实体的真实值填入 query 模板。否则 oracle 不只提供结构，还泄露了绑定答案。

## 6.3 后续训练的边界

保留共享模型、多任务接口的思路。是否进行 SFT 或轨迹优化，等接口和机制对照完成后再决定。原 V5 的奖励条目如继续使用，需要把 triple-level 信号改成 fact routing、绑定正确性、候选提升和完整证据支持等信号；本文不提出新的已验证训练收益。

# 7 实验设计：把表示变化和机制变化分开

## 7.1 不变项

原数据划分、文本扩展方式、顺序变体、模型版本、采样参数、答案评测和基线记录继续冻结。本文不重新选择模型，不更改历史结果，也不把原文中的模型表当作已经完成的新一轮验证。[原版对应：V5 §7，pp.24–29]

## 7.2 第一组：同证据条件下的表示对照

固定一组来源事实和同一 Answer 接口，比较三元组表达、自然语言事实列表，以及增加绑定衔接信息的事实图表达。先确保各版本的来源、限定条件和对象对应信息一致；再在相同 token 预算下比较实际效果。

这一组回答“模型更容易使用哪种表示”，不评估早期证据是否会被保存。不能把金标准证据输入下的效果直接当成完整框架效果。

若事实列表与事实图表现相同，应如实说明显式边在回答阶段未显示额外收益。边仍可作为 Runtime 的来源和依赖记录，但不应因此声称图展示本身提高了准确率。

## 7.3 第二组：流式机制对照

| 版本 | 保持一致的部分 | 主要检验点 |
|---|---|---|
| V5 原版 | 固定数据、模型和预算；保留原版自身流程 | 保留一个未经偷改的基线 |
| V5.1 完整版 | 自然语言计划、完整事实、绑定候选复核 | 新框架整体是否有效 |
| V5.1：不看 DORMANT | 其余同完整版 | 早期需求感知是否提高证据召回 |
| V5.1：有 DEFER、无历史回调 | 保存候选但不主动接回 | 保存与恢复是否都不可缺少 |
| V5.1：候选全部直接入活跃记忆 | 使用相同上下文上限，完整统计超限与筛选 | 外部候选隔离是否有价值，代价是什么 |
| V5.1：事实列表回答 | 管理流程不变，仅不显示事实边 | Answer 是否真正受益于显式连接 |

若想单独隔离“移除 Runtime 最终运算”的影响，应另设并明确命名适配版，不能修改原 V5 后仍称为原版。

原来的 `w/o relation family` 与 `w/o exact callback` 不再是新版的直接消融名称。前者对应的是另一套表示设定；后者应改成“无绑定触发候选复核”或明确的自由语义检索变体。

## 7.4 指标修改

保留 Answer EM/F1、Supporting-Fact EM/F1、Reverse–Forward Gap、调用成本和运行失败率等原有指标，新增或重新定义以下指标。

| 指标 | 测量内容 |
|---|---|
| 早期候选保存召回率 | 后来有用的早期事实，是否在输入对象未确定时被保存 |
| query 路由正确性 | 事实是否分配给可用的证据需求，而不是仅主题相似 |
| 提升精确率与召回率 | PROMOTE 是否匹配当前对象；真正可用候选是否被接回 |
| 绑定正确性 | BIND 的对象、值和支持是否正确 |
| 完整支持保留率 | 至少一组有效支持是否完整保留，避免平均召回掩盖桥接丢失 |
| 陈旧绑定残留率 | 上游纠错后，下游是否还在使用旧接受记录 |
| 成本分解 | PLAN、UPDATE、VERIFY、ANSWER 的输入/输出 token；复核候选数、来源恢复量、活跃峰值与外部存储 |

标注只给出一条支持链时，不能把其他有效支持路径直接判成无效；将标注事实匹配与实际证据支持性分开分析。也不默认数据集中每题都具有多条支持链。

# 8 论文表述与预期贡献的同步修改

## 8.1 可直接替换的方法概述

> 本方法采用自然语言依赖计划引导长文档的顺序阅读。计划节点描述待获取的证据信息，节点之间通过尚未确定的输入变量形成依赖。阅读器同时关注已激活和未激活的证据需求，将原文支持的完整事实作为基本记忆单元：能够匹配当前具体对象的事实进入活跃工作记忆，对象尚未确定的相关事实进入外部延迟候选区。当后续证据产生新的变量绑定时，Runtime 实例化相应子问题，定向恢复历史候选及原文，由共享 Agent 核验后将匹配事实接入工作记忆，并继续传播新绑定。工作记忆只保存与当前任务相关的可追溯事实及必要的绑定衔接，最终由同一模型的 Answer 接口基于这些证据完成综合推理。

## 8.2 保留与删除的贡献表述

保留“事实内容与任务用途分离”“绑定触发候选恢复”“事件驱动而非全量重写”“计划与事实工作记忆分离”“来源可追溯”和“单共享 Agent”等设计重点。

删除或替换“以 verified triples 为唯一表达”“开放三元组统一所有题型”“主要依靠 relation family 实现精确语义回调”“Runtime 完成所有推理”“必须生成 DERIVED triple”和“保证得到最小证据子图”等依赖旧机制的表述。

本轮没有新的系统性文献核查，因此不写“此前无人研究自然语言依赖计划或事实节点”。预期贡献应围绕延迟绑定机制及其可测量效果，等待实验验证。

## 8.3 推理开销表述

原 V5 §8.5 的稀疏事件成本分析不能原封不动迁移。[V5 p.31]

新版仍可能减少全量工作记忆改写，但自然语言候选复核会增加输入和输出。成本至少分为计划、逐窗阅读、各次候选复核、最终回答四部分。对于很多候选共享同一宽泛 query 的情形，复核成本可能较高。

因此只提出“稀疏事件与候选隔离可能改善成本分配”的假设，不宣称必然节省 token 或 wall-clock 时间。比较时同时报告候选区规模与每次回调读取量。

# 9 主要风险与对应约束

| 风险 | 本轮采用的约束 | 不应作出的承诺 |
|---|---|---|
| 通配对象造成候选过多 | 保留关系方向和限定条件；按 query 分桶；激活后分批复核 | 外部存储使候选成本消失 |
| 自然语言关系误匹配 | 具体 query + 原文 + 当前对象依据一同核验 | 换成自然语言后无需验证 |
| 同名或代词混淆 | 保留来源与消歧依据；不确定时不强绑定 | 字符串一致就是同一实体 |
| 初始计划遗漏 | 保留原问题、PLAN_HINT 和局部修正 | 计划改了就能恢复所有从未保存的事实 |
| 早期结果错误传播 | 绑定版本、支持追踪、下游失效与重核 | RESOLVED 永久正确 |
| 集合未完整就回答 | 明确 OPEN / CLOSED 边界 | 找到一个成员就解决集合 query |
| 轻量输出仍解析失败 | 固定语法、合法来源校验、记录修复成本 | 去掉 JSON 就一定不降准确率 |
| 活跃记忆超预算 | 可恢复视图、完整统计最终证据包大小 | 任意长支持链都能无损塞入固定预算 |
| 显式边没有额外效果 | 设置事实列表对照，必要时仅保留内部连接记录 | 只要叫“图”就有增益 |

# 10 最小实施路线与验收

## 10.1 模块级修改清单

| 现有职责 | 必须修改 | 优先复用 |
|---|---|---|
| 计划生成与解析 | 支持自然语言模板、占位符、依赖和三种状态 | 原模型调用封装、计划版本日志 |
| 阅读提示词 | 同时展示 ACTIVE / DORMANT 需求；输出完整事实和短标记 | 原窗口读取、source ID |
| 事件解析 | 增加 Fact Event、BIND；取消必填三元组和 family | 原校验、重试、日志设施 |
| 事实存储 | 事实为节点；状态按 query 和绑定实例记录 | 原来源、限定条件与归档 |
| 候选区 | 建 query_id 候选索引，保留多 query 引用 | 原外部存储和去重机制 |
| 绑定与状态管理 | 验证结果后更新状态；传播依赖；支持失效重核 | 原控制循环和事件队列 |
| callback | 从 exact semantic lookup 改为 query 候选复核 | 原 FETCH、VERIFY 调用框架 |
| 回答输入 | 紧凑事实证据包，不强制 Operator Trace 或全图 JSON | 已验证的 direct 回答与评测格式 |
| 评测日志 | 添加候选保存、复核、提升、绑定及版本信息 | 原离线重放和成本统计 |

## 10.2 实施顺序

**阶段 A：接口可用。** 先完成 PLAN、Fact Event、BIND 解析，保证来源检查与状态更新。用人工计划和短事实测试，不立刻改训练。

**阶段 B：闭环跑通。** 完成 query 候选桶、绑定触发复核、多跳连续传播、同窗口批处理、幂等与基本纠错。跑附录 C 的离线案例。

**阶段 C：回答兼容。** 使用同一组固定事实，对比新版 Evidence Pack 与既有 direct 输入输出，先排除格式引入的性能变化。

**阶段 D：小规模流式对照。** 冻结模型和预算，在同一批题上跑原 V5 与 V5.1，并运行“无 DORMANT 感知”“无候选回调”两个关键机制消融。

候选筛选优化、学习式保留、复杂集合扩展和新训练奖励都不属于这轮的前置任务。

## 10.3 验收标准

验收应区分流程正确和性能改进。附录 C 的案例通过，说明关键状态逻辑符合设计；只有正式对照实验才能说明准确率或成本是否改善。

至少应能从日志重放：事实何时被读到、为什么 DEFER、何时绑定、复核了哪些来源、何时 PROMOTE、最终用了哪些事实。出现错误绑定时，能够定位支持来源和受到影响的下游 query。

本次交付后的目标状态是“可实现、可验证的修改方案”，不是“已经证明优于 V5”。

# 附录 A 四类接口的提示词模板

以下模板可直接作为实现起点。方括号内为程序注入内容；模型输出协议固定，不要求模型生成内部状态字典。正式实验中应锁定模板版本。

## A.1 PLAN

```text
你需要为顺序阅读长文档制定证据收集计划。

原问题：
[QUESTION]

把原问题拆成少量自然语言子问题。
每个子问题描述一项需要获取或确定的信息，使用完整问句。
后续子问题可用 ?变量 引用前序子问题的输出。

要求：
1. 只根据原问题规划，不填入需要阅读文档才能知道的答案。
2. 只保留必要的依赖，允许并行分支，依赖必须无环。
3. 每个输出变量有唯一的产生节点；每个输入变量有已声明来源。
4. 只用于最终答案的比较或归纳，通常不建立额外节点。
5. 某个中间结论决定后续寻找对象时，允许增加自然语言选择节点。
6. 不输出三元组、relation family、运算代码或事实图。
7. 遇到完整枚举需求，在问题中明确“全部/所有”，并注明集合需求。

输出格式：
Q1
query: ...
output: ?...
depends_on: NONE

Q2
query: ...
output: ?...
depends_on: Q1

不要输出真实结果或自行决定执行状态；状态由程序计算。
```

## A.2 UPDATE

```text
你正在顺序阅读文档，为原问题收集有原文依据的事实。

原问题：
[QUESTION]

子问题计划与当前状态：
[QUERY_PLAN_VIEW]

已接受的活跃事实与必要绑定依据：
[ACTIVE_FACTS]

当前文本片段及来源编号：
[CURRENT_WINDOW]

同时检查 ACTIVE 和 DORMANT 子问题。

对 ACTIVE：
收集支持其具体对象和证据需求的完整事实，标记 COMMIT。
仅当证据足够支持该子问题的结果时，额外输出 BIND。
有用事实不等于完整答案，不要因 COMMIT 自动认为问题已解决。

对 DORMANT：
?变量 表示尚未确定的输入对象或值。
可以用原文中的具体对象暂时代入，但保留 query 的关系、角色方向、
否定、时间与范围要求。符合证据需求的完整事实标记 DEFER。
不要据此倒推或填入尚未得到支持的上游变量。

始终保留事实中的具体对象，不用 ?变量 替换原文中的人名或数值。
不要凭空补全代词；规范化所需的依据必须出现在可引用来源中。
不能仅因共同关键词或共同主题就判定相关。
若当前片段明显挑战某个 RESOLVED 子问题的关键事实或结果，
输出对应 query 的完整新事实，标记 DEFER，并用 PLAN_HINT 简述冲突。
程序会复核这一事实，不得因为 query 已解决而忽略反证。
不重写整张工作记忆，不输出没有来源的事实。

事实格式：
query_id | source_refs | 完整事实 | COMMIT或DEFER

结果格式：
BIND | query_id | 结果值 | 支持结果的source_refs

若某条原文证据明显有助于原问题，但现有计划无法容纳，输出：
PLAN_HINT | source_refs | 具体证据与所缺需求的简短说明

无相关事实时输出 NONE。不要追加解释性长文。
```

## A.3 VERIFY：候选复核与必要的结果确认

```text
你需要核验历史候选能否用于当前已经具体化的子问题。

原问题：
[QUESTION]

当前子问题与输入绑定：
[INSTANTIATED_QUERY_AND_BINDINGS]

绑定的支持来源与当前已接受事实：
[BINDING_SUPPORT_AND_ACCEPTED_FACTS]

本批候选、fact_id、source_refs 及对应原文：
[CANDIDATES_AND_RAW_SPANS]

逐条核验：
- 原文是否支持候选陈述；
- 是否与当前目标对象一致，不能仅按同名认定；
- 是否符合当前子问题的关系方向和限定条件；
- 是否提供相关限制或冲突，而不是正向答案。

判定：
MATCH：原文支持，且可用于当前子问题。
MISMATCH：不适用于当前对象或证据需求。
UNCERTAIN：当前来源不足以确定适用性。
CONFLICT：与当前结果或已接受证据存在需处理的冲突。

每条输出：
fact_id | 判定

只有已接受事实与本批 MATCH 证据足以支持结果时，才提出：
BIND | query_id | 结果值 | 支持结果的source_refs

BIND 只是建议。程序会合并当前候选桶各批判定后检查冲突再应用。
不得忽略否定，不得填入无法由输入证据支持的结果。
不生成新的原文事实，不输出大段推理过程。
```

充分性检查可复用该接口：把目标设为原问题，输入最终候选证据包，要求判断证据支持是否充分、是否仍存在关键缺口或冲突。此判断不等于独立模型证明，应在评测中检测错误放行。

## A.4 ANSWER

```text
原问题：
[QUESTION]

可用证据：
[EVIDENCE_PACK]

根据原问题与这些证据作答。
你可以进行必要的比较、关系推理、归纳或计算。
区分不同人物、时间和范围，不把缺失的证据当成已知事实。

按照下面既有任务格式输出：
[EXISTING_BENCHMARK_ANSWER_CONTRACT]
```

不要在迁移记忆表示时改动最后的答案合同。若 benchmark 需要支持事实，沿用对应格式；若只需要短答案，不额外强制 JSON 或长解释。证据不足策略由统一实验协议规定。

# 附录 B 控制流程伪代码

下面用于说明调用与状态顺序，不是可直接替换仓库的完整实现。`verify` 等函数调用共享 Agent；存储、检查和队列操作由 Runtime 执行。

```text
initialize(question, document_schedule)
plan = PLAN(question)
validate_plan(plan)
recompute_status(plan)

for window in document_schedule:
    archive.add_observed(window)
    view = make_bounded_view(question, plan, active_facts, window)
    response = UPDATE(view)
    events = parse_and_validate(response, observed_sources=archive)

    # 先登记全部事实，确保同窗口的下游证据已可查。
    fact_events, bind_events, hints = split_events(events)
    for event in fact_events:
        fact_id = store_source_grounded_candidate(event)
        apply_fact_for_query(event, fact_id, current_bindings)
        if query_inputs_ready(event.query_id) and needs_review(event):
            queue_review(event.query_id)

    record_plan_hints(hints)

    # BIND 只有在引用证据合法、依赖已满足时才可能被接受。
    for proposal in bind_events:
        if validate_binding_support(proposal):
            accept_or_hold_for_conflict_check(proposal)
            queue_affected_queries(proposal.query_id)

    # 新绑定可在同一轮连续触发多跳，不等下一个文本窗口。
    while event_queue is not empty:
        query_id = event_queue.pop()
        recompute_status(plan, query_id)
        if query_is_dormant(query_id):
            continue

        query = instantiate_without_overwriting_template(query_id)
        candidates = unseen_candidates_for_current_versions(query_id)
        judgments = []
        proposals = []

        for batch in budgeted_batches(candidates):
            raw = archive.fetch_observed_sources(batch)
            result = VERIFY(query, binding_support, batch, raw)
            judgments.extend(validate_judgments(result))
            proposals.extend(result.binding_proposals)

        promote_matches(judgments, with_binding_provenance=True)
        record_mismatch_uncertainty_and_conflict(judgments)
        # 当前已知桶的结果合并后再确认，避免只看首批。
        binding = reconcile_supported_proposals(proposals, query_id)
        if no_acceptable_binding(binding) and fresh_usable_evidence(query_id):
            # 联合多个批次的 MATCH 事实，或利用已就绪的上游事实。
            # 复用同一 VERIFY 接口；相同证据签名只尝试一次。
            joint = VERIFY(query, accepted_support_bundle(query_id))
            binding = validate_joint_binding(joint, query_id)
        if binding_is_new_and_acceptable(binding):
            apply_binding(binding)
            queue_affected_queries(query_id)

    handle_required_local_plan_patch_without_future_access()
    refresh_bounded_active_view()
    log_events_versions_and_all_costs()

# 第一轮实验默认完整扫描，不把早停混入表示修改。
pack = build_traceable_evidence_pack()
verdict = check_sufficiency(question, pack, runtime_constraints)
answer = ANSWER(question, pack, fixed_answer_contract)
record(answer, verdict, unresolved_queries, conflicts, budget_failures)
```

上游结果修正时，应先使受影响的下游接受记录失效、更新绑定版本，再加入复核队列。重复事件在相同版本下不应产生重复事实、重复连接或无限调用。

# 附录 C 离线逻辑验收案例

以下是实现验收用的合成案例，不是新的 benchmark，也不是性能结论。可先用模拟 Agent 输出测试 Runtime，再用真实模型测试接口行为。

| 编号 | 场景 | 必须满足的行为 |
|---|---|---|
| T01 | 根 query 输入已知、输出未知 | 状态为 ACTIVE，不能因存在输出变量而 DORMANT |
| T02 | 先出现 Alice 的母亲事实，老师未确定 | 为母亲 query DEFER，保留 Alice，不绑定老师或母亲结果 |
| T03 | 后出现 Cindy 的老师是 Alice | 激活母亲 query，复核原文，匹配事实 PROMOTE |
| T04 | 老师、母亲、出生地证据完全逆序 | 最后一个窗口触发连续两次回调，完成链条 |
| T05 | 多跳证据出现在同一窗口、事件顺序不同 | 先保存再绑定，两种输出顺序得到相同可用事实 |
| T06 | Alice 是老师，但没有母亲关系 | 不能仅按 teacher 关键词匹配母亲 query |
| T07 | Alice 的母亲不是 Mary | 保留否定，不能 BIND 母亲为 Mary |
| T08 | 原文包含两位同名 Alice | 缺少同一性依据时，不按名字直接拼接 |
| T09 | 一个事实关联两个 query | 正文只存一份，使用状态按 query 分别维护 |
| T10 | 第一批候选支持 Mary，后一批存在冲突 | 合并当前桶判定后处理，不能提前忽略冲突 |
| T11 | ?teacher 从 Alice 更正为 Bob | 旧下游接受记录失效；原事实保留；Bob 候选可重新核验 |
| T12 | 相同事件重复提交 | 不重复提升、不重复连接、不无限回调 |
| T13 | query 已 ACTIVE 后才到达新 DEFER 候选 | 新候选进入复核队列，不因“没有新激活”而永久沉睡 |
| T14 | 事实涉及最终年龄比较 | 保存身份与出生证据；不要求生成比较节点；交给 Answer |
| T15 | 年龄比较决定后续出生地对象 | 允许有来源的中间 BIND，再激活下一 query |
| T16 | 集合只出现一个成员但范围尚未闭合 | 不将完整集合 query 标为 RESOLVED |
| T17 | 事件引用未读或不存在的来源 | 拒绝应用并记录，不从未来原文补齐 |
| T18 | 事实正文中出现“defer”这个词 | 不靠全文关键词判动作，只解析规定位置的标记 |
| T19 | 计划修正后，历史候选可能重新相关 | 更新版本、重路由已保存候选，不复用过时判定 |
| T20 | 原计划有冗余节点，但已有直接充分证据 | 可经原问题充分性检查回答，不被冗余节点锁死 |
| T21 | 必要证据超出活跃预算 | 记录并处理预算瓶颈，不能无日志丢弃桥接依据 |
| T22 | 代词事实需要前一句才能补全主体 | 保存补全所需的全部来源；无依据时不规范化为确定人名 |
| T23 | 结果需要不同复核批次中的两条 MATCH 事实 | 合并已接受事实后可联合确认，不因每批单独不足而永久不绑定 |
| T24 | 中间选择 query 无候选，但上游证据已齐备 | 通过同一 VERIFY 的结果确认模式生成有来源的中间绑定 |
| T25 | RESOLVED query 在后续窗口遇到明确反证 | 仍接收、复核和纠错，不因状态为已解决而漏看 |
